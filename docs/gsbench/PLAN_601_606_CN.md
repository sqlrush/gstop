# gsbench 601–606 三阶段执行计划跳变手册

适用版本：gsbench v1.1.8

## 1. 使用前提

- 已执行 `gsbench init`，目标 schema 中存在 `plan_data` 及计划场景索引。
- 先查看 `gsbench doctor` 和 `init` 的 `PRECHECK_WARN`；告警不会阻止故障模拟。
- 601–606 共用计划对象，建议同一时间只测试其中一个场景；不符合此建议时程序仅告警。
- 恢复 DDL/DML 不由 gsbench 执行，用户必须自行评估锁等待和执行时间。

## 2. 两个终端、三个阶段

以 601、10 个固定 worker、持续造流 5 分钟为例。

终端一：建立基础流量。基线准备完成并显示 `RUNNING` 后才开始计算 `--duration`。

```sh
gsbench run 601 init --worker 10 --duration 5m
```

终端二：同步注入一次故障，SQL 完成后命令退出；终端一的 worker 不会重建或停止。

```sh
gsbench run 601 fault
```

观察到计划跳变后，在终端二展示该场景的恢复 SQL：

```sh
gsbench run 601 recover
```

`recover` 是只读规划命令，不执行输出的 DDL/DML。用户执行恢复 SQL 后再次运行，它会只读复核并标记 `ALREADY_RESTORED` 或继续显示待处理项。`recover` 不依赖 init 继续存活。

终端一第一次收到 Ctrl+C 就停止流量并关闭本次 tagged 会话。若 fault 已执行，必须查看同编号 `recover` 输出并由用户决定是否执行。

## 3. 场景与故障动作

| 编号 | 场景 | fault | recover 展示内容 |
|---|---|---|---|
| 601 | 唯一键索引删除 | 删除 `plan_data_lookup_idx` | 按 `(lookup_key,dist_key)` 唯一定义重建索引 |
| 602 | 唯一点查统计信息错误 | `lookup_key SET (n_distinct=1)` 后 ANALYZE，三条点查全部变为 Seq Scan | `RESET (n_distinct)` 后 ANALYZE，三条点查全部恢复 `plan_data_lookup_idx` |
| 603 | 伪造 n_distinct | 设置低统计目标和 `n_distinct=1` 后 ANALYZE | RESET n_distinct、恢复统计目标后 ANALYZE |
| 604 | 删除扩展统计 | `DELETE STATISTICS` 后 ANALYZE | `ADD STATISTICS` 后按扩展统计模式 ANALYZE |
| 605 | 删除索引 | 删除 `plan_index_drop_idx` | 按标准列定义重建索引 |
| 606 | 错误复合索引列序 | 删除 good 索引并创建 bad 索引 | 删除 bad 索引并重建 good 索引 |

601 的 worker 持续轮换复合唯一键等值点查：

```sql
SELECT id,payload
FROM <schema>.plan_data
WHERE lookup_key=<唯一查找键>;
```

基线索引为：

```sql
CREATE UNIQUE INDEX plan_data_lookup_idx
ON <schema>.plan_data (lookup_key,dist_key);
```

`fault` 删除该索引后，后续点查将失去专用访问路径并退化为全表扫描；
`recover` 展示重建完全相同唯一索引的 DDL。`init` 发现索引缺失或定义不同时只告警，
不会转换或重建。未显式指定索引方法时，普通表 `btree` 与 Ustore 返回的 `ubtree`
视为等价；显式方法要求仍严格匹配。

602 与 601 使用完全相同的三条 `lookup_key` 唯一点查流量，但不删除、不禁用、
不重建索引。故障和恢复 SQL 为：

```sql
-- fault
ALTER TABLE <schema>.plan_data
  ALTER COLUMN lookup_key SET (n_distinct=1);
ANALYZE <schema>.plan_data(lookup_key);

-- recover
ALTER TABLE <schema>.plan_data
  ALTER COLUMN lookup_key RESET (n_distinct);
ANALYZE <schema>.plan_data(lookup_key);
```

`fault` 的统计信息 DDL/DML 真实执行失败时场景失败；SQL 成功但计划未全部变为
`Seq Scan` 时输出告警并保留故障现场。`recover` 只展示 `RESET` 和 `ANALYZE`，
不会执行，也不会清空 journal。用户执行后再次运行 `recover` 可复核计划是否回到
`plan_data_lookup_idx`；计划仍不符合预期时继续输出告警。

602–606 的操作命令与 601 完全一致，只替换三条命令中的编号。例如：

```sh
gsbench run 605 init --worker 10 --duration 5m
gsbench run 605 fault
gsbench run 605 recover
```

## 4. 参数和状态

- `--worker N`：准确创建 N 个固定客户端 worker；`--workers N` 是兼容别名，不能和 `--worker` 同时使用。
- `--duration D`：从 worker 全部就绪并显示 `RUNNING` 后开始计算的造流时间。
- `fault`：必须在同编号 init 存活时启动；不接受 worker、duration 或 run ID。
- `recover`：按场景只读发现并展示待恢复 DDL/DML；不接受 worker、duration 或 run ID。
- `recover` 本身即为只读预览，不需要 `--dry-run`。
- `gsbench restore`：展示所有场景的恢复 DDL/DML/人工动作，可用 `--run-id` 过滤。
- `gsbench status`：显示基础流量、故障记录和 stale/manual-recovery 提示，不代表 SQL 已自动恢复。

`run.validation_enabled` 在 v1.1.8 中只为兼容配置保留。计划、索引、统计信息和数据检查始终只输出告警；gsbench 不执行基线修复、逆操作或全表统计刷新。真实 fault SQL 错误仍使当前场景失败。

## 5. 异常处理

- 从旧版升级时保留原 `meta_journal` 和本地 ledger；执行同编号 `recover` 查看历史逆操作 SQL，人工核对并执行，不要重复注入 fault。
- 旧版 602 journal 中可能保存 `ALTER INDEX ... REBUILD`；v1.1.8 会原样展示历史动作，不自动执行。人工恢复旧故障后再注入新版统计信息故障。
- init 提示已有活动场景或计划对象异常时会继续运行并输出告警；如已有 fault，先查看 recover 建议。
- fault 提示 workload not running：对应 init 尚未显示 RUNNING、已到期或已退出，不能注入故障。
- fault 中途被终止：重新执行同编号 recover 查看 journal 中已记录的恢复动作。
- 下次 init 会自动把已退出进程遗留的 `workload_running` 元数据标记为 stale 后继续。
- `stop` 和普通 `cleanup` 只停止 tagged 会话；`cleanup --data` 才会在所有权校验后删除整个测试 schema。

运行日志中的数据库密码始终应显示为 `<redacted>`。
