# gstop v1.6.2 Schema-Qualified Plan Diagnosis Design

## Context

Scenario 601 runs a schema-qualified point lookup such as:

```sql
SELECT id,payload
FROM "gsbench_e2e_20260801_100g".plan_data
WHERE lookup_key=500000;
```

After `gsbench run 601 fault`, openGauss correctly drops
`plan_data_lookup_idx` and the current plan becomes a sequential scan. The text
plan, however, reports only `Seq Scan on plan_data`. The test database contains
three different schemas with a `plan_data` table. gstop therefore searches the
catalog by the bare relation name, finds multiple rows, reports an ambiguous
table, and suppresses the index diagnosis even though the full SQL identifies
the target schema.

The preceding 601 baseline preparation also emits `ANALYZE` statements. Their
historical plans contain intentional sequential scans; they are maintenance
operations and must not be presented as missing-index candidates.

## Goals

- Resolve a plan relation to the schema explicitly named by the SQL when the
  mapping is unique and safe.
- Prefer schema-bearing current plan evidence when the server supports verbose
  EXPLAIN output.
- Preserve the existing refusal to guess for genuinely ambiguous joins or SQL.
- Mark `ANALYZE` and `VACUUM` index advice as not applicable.
- Keep historical real plans for display while using current evidence and the
  current catalog for index diagnosis.
- Ship and locally deploy gstop v1.6.2 only after a real og5 601
  init/fault/recover verification succeeds.

## Non-goals

- Reconstruct the exact DDL of every dropped production index.
- Change gsbench workload SQL or the 601 fault/recovery contract.
- Hide arbitrary administrator queries from Top SQL.
- Infer a schema from `search_path` when neither SQL nor plan identifies one.

## Design

### 1. Schema evidence from the current plan

Safe EXPLAIN will first request verbose text output. A verbose plan that includes
`schema.table` is parsed through the existing plan-analysis path. If verbose
syntax is unavailable on a supported server variant, gstop falls back to the
current non-verbose EXPLAIN behavior rather than losing the plan.

### 2. Safe schema binding from full SQL

Before catalog diagnosis, unresolved `TableAccess` values are enriched from the
full SQL text. The binder uses lexical SQL tokens rather than substring
matching, ignores comments and string literals, handles quoted identifiers, and
collects schema-qualified relation references from relation-bearing clauses.

An unresolved plan access is bound only when exactly one SQL relation has the
same table name and an explicit schema. If two different schemas contain the
same referenced table name in the same SQL, or aliases cannot be matched
unambiguously, the access remains unresolved and the current safety warning is
retained.

This binding is evidence enrichment only. It never rewrites or executes user
SQL.

### 3. Catalog diagnosis

The catalog stage receives both plan-derived accesses and the SQL text used for
that plan candidate. Once the target is bound to
`gsbench_e2e_20260801_100g.plan_data`, existing column validation and current
catalog checks continue unchanged:

- validate `lookup_key` against `pg_attribute`;
- observe that `plan_data_lookup_idx` is absent from current `pg_index` data;
- retain the historical index name as deletion evidence;
- generate a display-only index candidate for the target schema.

Historical-plan display priority and catalog-generation stale-result guards are
unchanged.

### 4. Maintenance statements

The detail target is classified from its leading executable SQL keyword.
`ANALYZE` and `VACUUM` remain visible with their historical plans and runtime
evidence, but the access section reports that index advice is not applicable to
the maintenance scan. No CREATE INDEX candidate is produced from these plans.

### 5. Failure behavior

- Unsupported verbose EXPLAIN: retry with the existing safe EXPLAIN form.
- SQL tokenizer cannot prove one schema: retain the current ambiguity warning.
- Catalog query failure: retain the existing explicit evidence limitation and
  suppress DDL.
- Context cancellation or stale asynchronous result: retain existing bounded
  cancellation and generation checks.

## Verification

### Automated regression tests

- Three catalog schemas contain `plan_data`; a schema-qualified lookup binds to
  only the named schema and produces an index recommendation.
- A query referencing two schemas with the same table name remains ambiguous.
- Quoted identifiers, aliases, comments, and string literals cannot create a
  false schema binding.
- Verbose EXPLAIN is preferred and non-verbose EXPLAIN is the compatibility
  fallback.
- `ANALYZE` and `VACUUM` never produce index DDL.
- Existing historical-display/current-catalog and asynchronous-generation
  regression tests continue to pass.

Run `go test ./... -count=1`, `go vet ./...`, and focused race tests for the
detail pipeline.

### Real og5 acceptance

1. Restore scenario 601 and confirm `plan_data_lookup_idx` plus Index Scan.
2. Start gstop v1.6.2 and establish a clean baseline without DB-memory errors.
3. Run `gsbench run 601 init --worker 2 --duration 2m`.
4. Run `gsbench run 601 fault` from another terminal.
5. Confirm SQL ID 3877360001 changes to Seq Scan and the detail page identifies
   `gsbench_e2e_20260801_100g.plan_data`, reports the missing historical index,
   and produces an index candidate containing `lookup_key`.
6. Run `gsbench run 601 recover` and confirm the plan returns to Index Scan.
7. Confirm no `palloc0`, `memory is temporarily unavailable`, or cross-database
   connection cascade occurred during the acceptance window.

After acceptance, atomically replace only
`/Users/sqlrush/gstop/gsbench-local/bin/gstop.real`; preserve the wrapper,
configuration, environment file, and a timestamped v1.6.1 backup.
