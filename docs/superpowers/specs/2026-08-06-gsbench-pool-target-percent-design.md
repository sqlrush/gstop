# gsbench 401/402 百分比目标设计

## 背景

gsbench 1.1.7 的 401 `connection_pool` 和 402 `thread_pool` 已支持配置文件中的 `target_percent`，默认值均为 95，但命令行不能覆盖该值。现有 401 会按连接容量补足会话，402 会持续调节压测 worker；用户需要在每次运行时显式指定百分比，并要求只补足压测前基线与目标之间的差值，达标后停止增加，保持已有压力至 `--duration` 结束。

本设计还要求目标不可达时明确失败、失败不取消同一次运行中的其他场景、结束时释放本次增加的资源，并对仅包含无持久化动作 401/402 的 stale recovery 失败提供受限的非阻断路径。

## 用户接口

新增统一参数：

```text
--percent N
```

示例：

```bash
gsbench run 401 --percent 90 --duration 5m
gsbench run 402 --percent 90 --duration 5m
gsbench run -s 301,401,402 --percent 90 --duration 5m
```

参数规则：

- 仅 `run` 命令可用；
- `N` 必须是 `1`–`100` 的整数；
- 所选场景中必须至少包含 401 或 402；
- 同一次运行同时包含 401、402 时，两者使用同一个命令行目标；
- 同一次运行中的其他场景不读取该参数；
- 命令行值覆盖所选 401/402 的配置值；
- 未传参数时继续分别读取 `scenario.connection_pool.target_percent` 和 `scenario.thread_pool.target_percent`，默认均为 95。

配置加载后使用类型化的池目标配置，不在场景运行时临时修改原始配置树。配置文件和命令行目标都校验为 `1`–`100`。

## 共同生命周期

401/402 在注入前采集一次压测前基线。目标百分比必须严格大于基线；小于或等于基线时直接失败，不创建任何压测连接或 worker。

`--duration` 继续表示 ramp 与 hold 共用的总时长：

1. 在 ramp 阶段从基线开始补足压力；
2. 达到目标后停止增加并冻结本次注入数量；
3. 已建立的连接/worker 保持工作，直到共享 duration 到期；
4. duration 到期后进入正常停止和清理；
5. duration 到期前没有达到目标时，该场景失败并清理。

目标是否达成是场景运行的强制条件，不依赖 `run.validation_enabled`。关闭运行时验证时仍可得到 `UNVERIFIED` 的模型验证结果，但目标不高于基线、容量不可达或实际未达目标始终产生 `FAILED`。

## 401：连接池目标

### 百分比口径

```text
可用连接上限 = max_connections - sysadmin_reserved_connections
基线百分比   = 压测前当前连接数 / 可用连接上限 × 100
目标总连接数 = ceil(可用连接上限 × target_percent / 100)
注入连接数   = 目标总连接数 - 压测前当前连接数
```

例如可用连接上限为 100，压测前已有 80 个连接，目标为 90%，则只创建 10 个压测连接。保留连接不进入压测预算，`safety.max_connections` 继续限制本次 gsbench 最多可创建的连接数。

### 达标与保持

Prepare 阶段在创建连接前完成以下判断：

- 目标不高于当前基线：失败；
- 可用 headroom 或 `safety.max_connections` 无法容纳所需注入连接：失败；
- 容量可达：记录固定的注入连接数。

Ramp 阶段创建该固定数量的 tagged connections。全部建立成功后即停止增加。Hold 阶段不因其他业务连接离开而继续追加；它只保持并检查本次创建的 tagged connections。任何本次连接意外丢失或执行错误都会使 401 失败并清理，避免冻结后静默扩大注入量。

## 402：线程池目标

### 百分比口径

402 只接受真实线程池指标：

```text
基线百分比 = (actual_workers - idle_workers) / actual_workers × 100
```

`actual_workers`、`idle_workers` 和 `pending_sessions` 来自 `dbe_perf.global_threadpool_status`。无法读取真实线程池状态时，402 不能证明百分比，必须失败，不能用 active backend fallback 报告达标。

402 不修改线程池大小。它创建压测会话，使数据库已有 worker 进入繁忙状态。清理时删除的是 gsbench 压测会话和本地 worker；数据库拥有的 worker 返回空闲，是否销毁空闲线程由数据库自身管理。

### 容量和达标

压测前先计算最多可新增会话数，它同时受到实例连接 headroom、`safety.max_connections` 和 `safety.max_workers` 限制。最大可达线程池利用率按“当前繁忙 worker + 最多可新增会话”计算；低于目标时在注入前失败。

Ramp 按反馈逐步增加压测会话：

- 实际利用率第一次达到或超过目标后立即停止增加；
- 保持当前注入数量进行连续采样确认；
- 确认期间低于目标时允许继续补足；
- 连续三次采样达到或超过目标后，冻结注入数量并进入 hold；
- 不要求恰好等于目标，线程粒度造成的最小超调允许作为实际值记录；
- 冻结后 worker 丢失或执行失败时不补建，场景失败并清理。

## 失败隔离

Runner 保持每个场景独立执行和清理：

- 单独运行 401/402 时，失败清理后命令非零退出；
- 同一命令选择多个场景时，401/402 的失败不取消其他场景；
- Runner 等其余场景完成后汇总结果，最终命令因存在失败而非零退出；
- 一个池场景的失败不会跳过另一个场景的 Stop 阶段。

## 正常结束与 Ctrl+C 清理

正常 duration 到期或场景失败时，Runner 使用独立 cleanup context 调用 Stop：

- 401 先停止 active worker，回滚 idle-in-transaction 事务，再关闭全部 tagged connections；
- 402 停止控制器和本地 WorkerGroup，关闭其全部数据库会话；
- 清理错误合并到场景失败结果，不能伪装成成功。

保留现有“一次 Ctrl+C 由操作系统立即终止 gsbench”的行为，不引入可能阻塞退出的信号等待。进程退出会关闭所有客户端 TCP socket，数据库随即结束对应会话并回滚未提交事务。下一次运行仍尝试 stale recovery，以收敛运行元数据和任何持久化动作。

## stale recovery 非阻断例外

默认安全规则不变：stale recovery 失败会阻止新运行。只增加一个可证明安全的例外。

恢复发现阶段从 `meta_runs.scenarios` 读取并解析每个旧 run 的场景编号。只有同时满足以下全部条件，stale recovery 失败才降级为告警并允许新运行继续：

1. 能成功读取并验证所有旧 run 的场景身份；
2. 每个旧 run 的场景列表非空且只包含 401/402；
3. database recovery journal 和 local recovery ledger 均没有任何未恢复 action；
4. 不包含 402 自动启用线程池产生的实例参数 mutation；
5. 新运行使用新的 run ID；旧 run 绝不被覆盖为成功，终态写入可用时保留 `RESTORE_FAILED`，WARNING 始终输出原始恢复错误。

如果恢复发现本身失败、场景身份缺失/非法、旧 run 包含其他场景或存在任何 action，恢复失败仍然阻断。这样不会放宽 601–606 的索引/统计信息恢复、实例参数恢复、锁场景或其他持久化变更的安全规则。

允许继续时输出明确 WARNING。残留连接会计入新运行采集的基线，因此目标小于或等于当前占用时仍会失败，不会继续叠加池压力。

## 数据和接口变更

- `CLIOptions` 增加池百分比字段和参数是否显式设置的解析状态；
- `Overrides` 携带命令行池目标；
- `BenchConfig` 增加类型化的 401/402 目标配置，场景不再直接读取这两个 raw key；
- `RestoreRun` 增加解析后的场景编号，用于安全分类；
- `RestoreSummary` 暴露足够的已发现 run 元数据，使启动编排层能够判断是否满足非阻断例外；
- RestoreCoordinator 的通用失败语义不改变，非阻断决策仅存在于新运行前的 stale recovery 编排层。

## 测试与验收

### CLI 与配置

- 接受 401/402 的 `--percent 1`、`--percent 90`、`--percent 100`；
- 同一运行的 401/402 获得同一覆盖值，其他场景保持原配置；
- 拒绝 0、负数、101、非整数、非 `run` 命令和没有选择 401/402 的用法；
- 未传参数时保留配置值和默认 95；
- 拒绝配置文件中越界的池目标。

### 场景行为

- 401 在基线 80%、目标 90% 时只创建剩余 10% 对应的连接；
- 401 在目标不高于基线或 safety/headroom 不足时注入前失败；
- 401 达标后不因外部连接退出而追加，本次连接丢失会失败；
- 402 在目标不高于基线、真实指标缺失或容量上限不足时注入前失败；
- 402 达标后停止增加，连续三次确认后冻结；
- 402 冻结后不补建失败 worker；
- 两个场景在 duration 到期前未达标时失败；
- 正常结束、场景错误和 context 取消路径均释放本次创建的资源。

### 隔离与恢复

- 一个场景失败时同一 Runner 中的其他场景仍完成自身生命周期；
- 仅包含无 action 401/402 的 stale run 恢复失败会记录 WARNING 并启动新 run，且绝不把旧 run 标成恢复成功；
- 旧 run 含其他场景、任何 action、未知场景或发现错误时继续阻断；
- 402 实例参数 mutation 存在时继续阻断；
- 保留现有一次 SIGINT 立即终止进程测试。

## 非目标

- 不提供 401 和 402 的两个独立命令行百分比；
- 不改变数据库线程池配置大小；
- 不保证业务连接或数据库自有 worker 在 hold 阶段保持不变；
- 不把失败的旧 recovery 标记为成功，也不删除旧失败证据；
- 不放宽除无 action 401/402 之外的任何 stale recovery 安全规则；
- 不改变其他场景的目标、并发模型或清理逻辑。
